- **Smaller graphs, shorter files** (`docs/DEV/DESIGN/graflang-use-cases.md`: what GraphLang is for, what it is not, and how to write Hello World). The create guide now says to use the fewest steps that meet the specification and not to add guards, code-running or branches silently. **The editor keeps `steps:` files short**: it edits the long form internally, shows the short form in the Source tab and saves it short (the saved file is checked by `graf compact` to expand to exactly the edited graph); it no longer converts a short file to the long one on opening. In the compact form, `in: {x: [a, b]}` means "whichever of these exclusive steps ran" (no duplicate wires where branches meet). New node **`RUN_CODE`** (compact `run_code: [python, javascript]`, `grafr/run_code.py`): runs the program text a step produced in a throwaway folder, never fails the graph, risky so a guard must precede it, `languages` is a code key. `cookbook/hello_world` is now 9 short steps (was 13 nodes, 30 edges), and README and the user guide say when not to use GraphLang. Tests: `tests/test_run_code.py`, `tests/test_editor.py`, `tests/test_compactify.py`.

- **Picture layouts:** `dot` is now top to bottom (the editor's default); a second choice, `dot horizontal`, lays the graph out left to right. (Before, `dot` picked a direction by itself to fit the window, which made a long workflow one wide row.) Change is in zinet (`dot_layouts(rankdir=...)`).

- **`cookbook/hello_world`: the program is run.** Both branches (`mode=llm`, `mode=solver`) now meet at a Cedar `GUARD` (`policies/run.cedar`: Python and JavaScript only) and then `tools/run_program.py` runs the program in a throwaway folder (empty environment, no input, 10 s limit) and returns what it printed as `result`. A model reply with no code block is run as it is; prose, a crash, a timeout or a missing interpreter come back as a note in `result`, never as an error. Tests in `tests/test_decision.py`.

- **`DECISION` node: a person as a node** (`grafr/decision.py`, design in `graflang-hitl.md`). It shows a question (and an `in_context`), takes one of `answers` or free text from the terminal (`answer | note`), or from `graf run --answer node=value[|note] --by NAME`, and routes by `answered` (with `out_answer`, `out_note`, `out_by`) or `timeout`. `default` is used when nobody answers; `graf validate` checks the config and warns when a defaulted `DECISION` can reach a risky node. A `MUTATE` delta can neither remove nor change it. Interactive mode only; the parked mode is not built. `cookbook/release_approval` (draft, person decides, Cedar guard, EMIT), `tests/test_decision.py`.

- **Composability steps 3, 4, 5 and 7.**
  - *By name (3):* `resources.parts` may say `cookbook:guardrail` (or `apps:`, `solvers:`) instead of a path; `cookbook:guardrail@<hash>` pins the recipe's files, and a changed recipe is refused with its new hash (`graf parts` prints it). The Browse page has "Use as a part of another workflow": the recipe's capabilities, cost and a snippet to paste.
  - *Boundary (4):* `graf parts FILE` lists each part a workflow uses with its interface, what it can touch (files read/written, e-mail, webhook, stdout, programs) and an upper bound on model calls. The using graph's `workflow.parts_policy: {forbid: [...], max_llm_calls: N}` is checked on `graf validate` / `graf run` (`grafr/partinfo.py`).

- **`graf compact`**, the inverse of `graf expand` (`grafr/compactify.py`): a long-form workflow (`nodes:`/`edges:`) written as `steps:`. It is exact by construction: the result is re-expanded and compared with the input (nodes with ports and config, edges, loop bodies), and any node whose step does not come back identical stays in `nodes:` (its edges in `edges:`). On the cookbook, `self_refine`, `chain_of_thought`, `guardrail`, `supervisor`, `self_heal` and `agent_notes` compact fully; `code_pipeline` and `your_book` only in part (back edges, `RECOVER` nodes and some loop bodies stay long). Comments and the order of nodes/edges are not kept. `tests/test_compactify.py`.

It is a test of the interface (each stage's text is the next one's `question`), not a product.

- **Recipes as building blocks** (composability steps 1 and 2, `docs/DEV/DESIGN/graflang-idea.md`): a part may now end in **several `OUTPUT` nodes** (a branching recipe ends each branch in its own), so `guardrail`, `supervisor`, `self_heal` and `agent_notes` can be used as one node of another graph. A `QUERY`'s or `EMIT`'s `file` inside a part is read from the **part's folder** (made absolute at expansion, the part's folder added to `allow_dirs`; a path that escapes both folders fails `graf validate`); a path passed in on a port stays the using graph's business. Fixed on the way: a `LOOP`, `BATCH` or `MUTATE` did not get an input's default (a part's optional input read by a loop was missing). `EMIT` accepts an `in_file` port like `QUERY`; `chat_memory` takes its memory path from an input and `notes_digest` reads its bundled notes (no `notes_file` input). `tests/test_composition.py`.
- **`QUERY`, `EMIT` and `OBSERVE` are real nodes** (they were pass-through stubs; `grafr/outside.py`). `QUERY` reads a file in the graph's folder (text, JSON, YAML or lines; `tail` keeps the last N lines; `default` when it is missing). `EMIT` writes a file, prints, posts to a webhook (`allow_hosts`) or sends e-mail to recipients fixed in the graph (the SMTP login is read from `GRAF_SMTP_USER` / `GRAF_SMTP_PASSWORD`). `OBSERVE` records what passes by (the log, and `observations.jsonl` in the run's folder) and can never fail or stop a run. `QUERY` and `EMIT` stay risky: `graf validate` accepts them only behind a `GUARD`. Paths cannot leave the graph's folder (links are followed first; `allow_dirs` lists others), and the keys that decide where they read, write or send are code keys a `MUTATE` delta can never set. In a dry run (the `mock` adapter) an `EMIT` only reports; `effects=True` makes it real. `graf validate` also warns when a retried `EMIT` or `RUN` may repeat its effect.

Result folders are now named `your_book-<adapter>-<model>-<time>`.

- `your_book` takes `audience` (`intro`, `intermediate`, `advanced`, `research`; default `intro`) and `style` (free text), and every prompt uses them: the outline, each chapter, the review (which now also checks fit to the audience and style), the revision and the compile step (a "How to read this book"). This replaces `target_audience`, which was declared but never reached a node.

- `your_book`: the second chapter could repeat the first. The chapter prompt was given the loop's 0-based counter ("write chapter 1") while the outline numbers chapters from 1; a `chapter_number` step now passes the 1-based number and the total.

- `your_book` revises: the reviewer's verdict now routes an `EVALUATE`; `REVISION_NEEDED` sends the chapter and the feedback to a new `revise_chapter` step, and the book is compiled from the revised chapters (before, the verdict was collected and never used). To collect "the chapter, revised or not", a LOOP's `collect` (and the compact `out:`) now accepts a list of results, taking the one written last in each iteration, as `from` already did.

- A list in a prompt: `{{in_chapters}}` used to show Python's repr (`['chapter 1\\n...', ...]`); a list of texts now reads one after another with a blank line between, and any other list or mapping as JSON. `your_book`'s compile step had been handed 13 KB of escaped text and answered "Okay" (the book came out empty); its nodes also no longer pin `ollama:gemma3`, so the run's `--llm` applies, and its prompts ask for the text only.

- `graf create --name N --spec TEXT|@FILE [--out-dir DIR] [--llm adapter:model] [--max-rounds N] [--allow-code] [--force]`: vibe-coding for GraphLang. An LLM writes an app (a compact `.graph.yaml`, its prompts, a readme) from a plain-language spec; the result is checked like `graf validate` and by a dry run on the mock LLM, and the problems go back to the LLM for up to `--max-rounds` calls. Nothing generated is executed without `--allow-code`. The authoring guide and three example apps are shipped in the package (`graphlang/grafc/create_guide.md`, `create_examples/`).

- A node's `config.model` is replaced by `config.llm: adapter[:model]` (the `--llm` spec). It beats the run's `--llm`, which beats the adapter default (`claude-sonnet-5-5` for `claude_cli`), so each task can choose its own model, or even its own adapter (created on first use; `llm.call` logs what ran). `:model` names a model on the run's adapter. `model:` on a GENERATE node is an error in `graf validate`; bindings `models:` / `model: $x` become `llms:` / `llm: $x`; the `mock` adapter answers every node. Before, the default acted as an override and node `model:` hints were ignored under `claude_cli`. A cassette records the default too (old ones still replay). SPL.py's lifter writes `llm: ":<model>"` for `USING MODEL`.

- `graf compile` takes `--lang rust|spl` (default rust) and `--dry-run`; `graf export-spl` is now `graf compile --lang spl`. Both languages run `graf validate`'s checks first and read compact, parts and elaborate files like `graf run` does. `graf check` is removed: it duplicated `validate` (schema, resources) and its extra analysis crashed on every graph; `graf compile --dry-run` is its replacement. `--target` is replaced by `--lang`.

## 0.1.0

First release: an early prototype. The graph (`*.graph.yaml`) is the program; the model changes the topology instead of writing code.

- `graf run`: token-passing dataflow over typed nodes (GENERATE, EVALUATE, SOLVE, ASSERT, LOOP, FORK/JOIN, GUARD, MUTATE, ...), with `--llm ADAPTER:MODEL` (default `claude_cli`; `--adapter mock` runs offline), run logs, and a results folder.
- Cedar `GUARD` and `MUTATE` checks (via `cedarpy`), fail-closed.
- `graf validate`, `graf info`, `graf check`; `graf compile` (Rust generator) is a stub and needs `pip install graflang[grafc]`.
- `graf vis`: draw a workflow (control flow first, data edges on demand, loops that collapse); engines cytoscape, graphviz, mermaid, ascii, and pyvis / graphify as extras.
- Shared libraries: dd-llm (adapters), dd-logging (logs), zinet (graph algorithms and drawing).
- The import package is `graphlang` (the PyPI name is `graflang`).
