# Changelog

## Unreleased

- `graf validate` reports an error for a `GENERATE` prompt (inline or `prompt_ref`) that uses `{{in_x}}` when the node has no port `in_x`, or nothing feeds it. Found in four lifted solver recipes, where a port had been named after an SPL function parameter and the model got the prompt unfilled.

- `backend: kernel` SOLVE nodes can run in another Jupyter kernel: `kernel_name` on the node, or `graf run --kernel-name NAME` for the nodes that name none (as SPL's `--kernel-name`), e.g. `sagemath`. One kernel per name is started per run. `cookbook_solvers/sage_math` is rewritten to use it and runs; `neurosymbolic`'s Sage rung runs under `--kernel-name sagemath`.

- `cookbook_solvers/demand_forecast`: the model that turns the problem text into JSON got only "Use the default 36-month widget sales dataset." and no data, so the solver found no forecast points; it is now given the default dataset (`in_default_problem_json`) to return when the text carries no data.

- A `procedure_ref` into an `.spl` file with several workflows ran the last one in the file. It now runs `config.workflow`, else the workflow named like the ref (`procedures.helper_b` runs `helper_b`), else the old choice (`procedures.workflow_names`, `declared_inputs(path, workflow)`).

- `cookbook_solvers/` (47 recipes lifted from SPL.py's `cookbook-solver`) was run end to end with `claude_cli` `claude-sonnet-5-5`: every graph completes except `sage_math` (needs SageMath). Fixes from the run: SPL token builtins in `constraint_opt`, GENERATE input ports renamed after the variables that feed them (`auto_planning`, `lean_proof`, `neurosymbolic`, `sql_verifier`), `run_python` of `lean_proof`/`neurosymbolic` runs in the shared kernel session (the Lean REPL persists), SPL library files copied next to the graphs that `IMPORT` them. `global_minlp` and `minizinc_cp` use their Python fallbacks unless Couenne/Bonmin or MiniZinc are installed.

- The Edit page's *Browse files* box has a **Folders** multiselect (apps, cookbook, solvers; all chosen to begin with) that filters the Recipe list.

- The expression language reads **f-strings**: `f'{@step_no}. {@line}\n'` in a `CONTEXT` expression or a condition. Each field is an expression under the usual whitelist; `!r`/`!s`/`!a` and a plain format spec (`{@x:.2f}`) work, fields inside a format spec, `=` and bytes f-strings are refused. They are rewritten to internal calls (`__fstr`, `__fmt`) before the parse, so nothing new can be called. This is what the lift of SPL's string building produced, and it unblocks `lean_proof`, `symbolic_math` and the other solver recipes that stopped at it.
- `graf vis --edit` adds `~/.graflang/solvers/` as a third, read-only root (after `apps` and `cookbook`): its recipes show on the Edit and Browse pages, are found for Create's examples, and are copied to `apps/` to edit. `workspace.solvers_dir()`; `--src-dir` still replaces all three.

- `graf describe PATH [-o FILE|-] [--force] [--llm [ADAPTER:MODEL]]` (`graphlang/grafc/describe.py`): PATH is a graph file or a recipe folder; the text is written to `RECIPE.spec.md` in the folder (`FILE.spec.md` beside a graph file), `-o -` prints it, an existing default is kept unless `--force`. Without `--llm`, a plain-language description built from the graph alone (no model): purpose, inputs and defaults, output, the steps in run order (prompts, function names and docstrings, conditions; `LOOP`/`BATCH` bodies nested), where each step's data comes from, and a count of model and program steps. With `--llm` one billed call has a model write a specification from that structure and the folder's readme, prompts, procedures, tools and policies (`build_spec_prompt`). It is the `--spec @FILE` for `graf create`, for the round trip `.spl` -> graph (spl2graph) -> specification (describe --llm) -> graph (create).

- New recipe `cookbook/stock_analysis` (lifted from SPL.py's `066_stock_analysis`, then reworked): Python fetches prices and computes metrics, a `BATCH` walks the list of tickers, the model comments on each and writes one outlook. The lift had made a `LOOP` over `@in_ticker IN @in_tickers`, which stops at once with `unknown variable @in_ticker`.

- The rest of the app review (`docs/DEV/DESIGN/graflang-UI.md`): `graf vis --edit` listens on `127.0.0.1` only (`--host` changes it, with a warning), because the app has no login and holds your API keys; the Edit page will not open another file, reload or copy over unsaved changes (the buttons are off, with the reason); the Run tab lists the nodes that run programs and asks you to tick before it runs them, and calls the mock "dry run"; Browse draws a picture only when asked; pictures and search-query vectors are made once instead of on every click; `GraphEditor` has `can_undo`/`undo_depth`; `workspace.program_nodes` names the nodes of a graph that run programs.

- Fixes from a review of the app (`docs/DEV/DESIGN/graflang-UI.md`): invalid YAML typed in a config box is an error message, not a crash; *Open in the Edit page* after Create works on a fresh session; a real-model run on the Edit page is capped in model calls (*Most model calls*, default 10; `GraphEditor.run(max_calls=)`); a Create draft can be saved again after a revision (replacing its own folder), and Undo takes the spec back too; the Edges tab's From/To follow the Type at once; Create asks for the name before it sends a message; Settings no longer saves unsaved edits when a key is removed, nor keeps the old provider's model name.

- `graf create` shows the model similar recipes too. The search lives in `grafc/create.py` (`find_examples`), and both `graf create` and the app's Create page use it. New options: `--examples/--no-examples` (default on), `--from RECIPE` (start from that recipe, e.g. `cookbook/self_refine`), `--src-dir DIR` (the work area to search) and `--embedding SPEC` (default: the app's setting). The command names the recipes it chose and says when they were found by words only. With an empty work area there are no examples.

- A **Welcome** landing page (`pages/00-welcome.py`) opens the app: what GraphLang is, what each page offers (with links), what the work area holds and the command line. `graf vis --edit FILE` still opens straight on Edit. `GRAF_PLAIN_EDITOR=1` makes the Source tab use a plain box instead of the Ace code editor (the tests do).

- Recipe search is by meaning as well as words. `graphlang/embedding.py` picks an embedding model through dd-embed (`embedding` setting: `auto` = sentence-transformers if installed, else a local Ollama model with "embed" in its name; `none`; or `provider:model`), caches recipe vectors in `~/.graflang/cache/`, and falls back to words when no model is available. `recipe_index` is now one entry per recipe, not per file (a recipe's sub-graphs and variants are listed under it), has a light stemmer ("coding" finds "code"), and returns only the best recipe and those close to it. On the cookbook with `qwen3-embedding:0.6b`: "coding" gives `code_pipeline`, "code pipeline" gives `code_pipeline` and `code_parts`, "cooking dinner" gives nothing. Create's examples use the same search and the chat says when they were chosen by words only. `dd-embed`, `numpy` and `requests` are now required dependencies; `graflang[semantic]` adds sentence-transformers.

- A fifth page, **Browse** (`pages/04-browse.py`), searches the recipes of the work area by what they do; `graphlang/recipe_index.py` is the index (BM25 over name, description, readme, node types, inputs and prompts, built in memory; the GraphLang counterpart of SPL.py's `spl3 code-rag`, without a vector database). Create uses it: the first message goes to the model with the best two matching recipes (not ones that run programs unless allowed) as examples, or the one chosen with *Use in Create* (`build_prompt(..., references=)`, `create_app(..., references=)`).

- `pyproject.toml`: `streamlit-ace` is now a required dependency (the Source tab's code editor), the `edit` extra is just `streamlit>=1.43`, and a new `solver` extra installs `sympy` and `z3-solver` for the `engine=sympy|z3` rule engines of `cookbook/compliance_audit`.

- Edit page: a **Source** tab (first, before Node) holds the whole `.graph.yaml` in a code editor for power users (`streamlit-ace` when installed, now in the `edit` extra, else a monospace box); **Apply** (`GraphEditor.set_source`) takes the text into the editor if it is YAML in the long form, undoably, and Save still refuses while `graf validate` finds errors. The sidebar's **Browse files** lists the graphs of a recipe including those in sub-folders (`graphs_in`, `Workspace.recipe_folder`), and copying a shipped recipe keeps the open file's place in it. A failed edit now shows its reason at once instead of at the next click. The `edit` extra needs `streamlit>=1.43`.

- The chat on the Create and Edit pages takes attachments: documents are read into the message (marked as material, not instructions; 30,000 characters each, up to 4 files), screenshots are passed to the model as image blocks (`images=` on `generate`; `DDLLM` accepts them only for adapters in `IMAGE_ADAPTERS`, now `anthropic`, and otherwise raises `LLMUnavailable` rather than dropping them). `create_app` and `revise_app` take `images`. `cookbook/code_parts/translator_spec.md` is a spec for re-creating the translator chat app from `meta-app-2026-10-31_14-12-38.png` as a workflow app.

- `graf vis --edit [GRAPH] [--src-dir DIR]` is now an app with four pages. **Create**: describe an app in a chat; the first message is the spec (as `graf create`), later ones revise it (`revise_app` in `grafc/create.py`), checked like `graf validate` plus a dry run, nothing written until Save. **Edit**: the editor, plus a chat that changes the graph through operations on the same editing methods (all or none, validated, comments kept, undoable; prompt files are staged until Save), a picker for the work area, and a read-only guard on shipped recipes (copy to your apps first). **Settings**: provider, model and API keys, saved in `~/.graflang/settings.json` (mode 0600). **Import / Export**: install the cookbook, import a zip or a graph file (never overwrites, refuses unsafe paths, lists programs), export a recipe as a zip. The work area is `~/.graflang/cookbook` (shipped, read-only) and `~/.graflang/apps` (yours), `$GRAFLANG_HOME` to move it, or one writable folder with `--src-dir`. The picture's top bar no longer overlaps the node panel (a zinet fix), and the sidebar is resizable, so the Split slider is gone. The pages are files in `graphlang/grafv/pages/` (`01-create.py`, `02-edit.py`, `03-transfer.py`, `99-settings.py`; the number orders them) behind a small entry script (`app.py`), and the picture is 800 pixels tall by default, set on the Settings page. The tabs on the right can be hidden with the *Editor panel* switch.

- `cookbook/concept_book` is now `cookbook/your_book` (graph `your_book.graph.yaml`, workflow `your_book`), so it is not mistaken for the concept-graph-driven ConceptBook: it writes a book on any subject, for a chosen audience and style. Result folders are now named `your_book-<adapter>-<model>-<time>`.

- `your_book` takes `audience` (`intro`, `intermediate`, `advanced`, `research`; default `intro`) and `style` (free text), and every prompt uses them: the outline, each chapter, the review (which now also checks fit to the audience and style), the revision and the compile step (a "How to read this book"). This replaces `target_audience`, which was declared but never reached a node.

- `your_book`: the second chapter could repeat the first. The chapter prompt was given the loop's 0-based counter ("write chapter 1") while the outline numbers chapters from 1; a `chapter_number` step now passes the 1-based number and the total.

- `your_book` revises: the reviewer's verdict now routes an `EVALUATE`; `REVISION_NEEDED` sends the chapter and the feedback to a new `revise_chapter` step, and the book is compiled from the revised chapters (before, the verdict was collected and never used). To collect "the chapter, revised or not", a LOOP's `collect` (and the compact `out:`) now accepts a list of results, taking the one written last in each iteration, as `from` already did.

- A list in a prompt: `{{in_chapters}}` used to show Python's repr (`['chapter 1\\n...', ...]`); a list of texts now reads one after another with a blank line between, and any other list or mapping as JSON. `your_book`'s compile step had been handed 13 KB of escaped text and answered "Okay" (the book came out empty); its nodes also no longer pin `ollama:gemma3`, so the run's `--llm` applies, and its prompts ask for the text only.

- `graf create --name N --spec TEXT|@FILE [--out-dir DIR] [--llm adapter:model] [--max-rounds N] [--allow-code] [--force]`: vibe-coding for GraphLang. An LLM writes an app (a compact `.graph.yaml`, its prompts, a readme) from a plain-language spec; the result is checked like `graf validate` and by a dry run on the mock LLM, and the problems go back to the LLM for up to `--max-rounds` calls. Nothing generated is executed without `--allow-code`. The authoring guide and three example apps are shipped in the package (`graphlang/grafc/create_guide.md`, `create_examples/`).

- A node's `config.model` is replaced by `config.llm: adapter[:model]` (the `--llm` spec). It beats the run's `--llm`, which beats the adapter default (`claude-sonnet-5-5` for `claude_cli`), so each task can choose its own model, or even its own adapter (created on first use; `llm.call` logs what ran). `:model` names a model on the run's adapter. `model:` on a GENERATE node is an error in `graf validate`; bindings `models:` / `model: $x` become `llms:` / `llm: $x`; the `mock` adapter answers every node. Before, the default acted as an override and node `model:` hints were ignored under `claude_cli`. A cassette records the default too (old ones still replay). SPL.py's lifter writes `llm: ":<model>"` for `USING MODEL`.

- `graf compile` takes `--lang rust|spl` (default rust) and `--dry-run`; `graf export-spl` is now `graf compile --lang spl`. Both languages run `graf validate`'s checks first and read compact, parts and elaborate files like `graf run` does. `graf check` is removed: it duplicated `validate` (schema, resources) and its extra analysis crashed on every graph; `graf compile --dry-run` is its replacement. `--target` is replaced by `--lang`.

## 0.1.1

- `graf vis`: nodes are labelled by what they do (`draft`, `write file`, `set iteration`, `repeat while ...`) with underscores shown as spaces, and show no type line (the colour and legend say it); the id and type are in the side panel. A node's `config.label` is used as written when present.
- Requires zinet 0.2.1.

## 0.1.0

First release: an early prototype. The graph (`*.graph.yaml`) is the program; the model changes the topology instead of writing code.

- `graf run`: token-passing dataflow over typed nodes (GENERATE, EVALUATE, SOLVE, ASSERT, LOOP, FORK/JOIN, GUARD, MUTATE, ...), with `--llm ADAPTER:MODEL` (default `claude_cli`; `--adapter mock` runs offline), run logs, and a results folder.
- Cedar `GUARD` and `MUTATE` checks (via `cedarpy`), fail-closed.
- `graf validate`, `graf info`, `graf check`; `graf compile` (Rust generator) is a stub and needs `pip install graflang[grafc]`.
- `graf vis`: draw a workflow (control flow first, data edges on demand, loops that collapse); engines cytoscape, graphviz, mermaid, ascii, and pyvis / graphify as extras.
- Shared libraries: dd-llm (adapters), dd-logging (logs), zinet (graph algorithms and drawing).
- The import package is `graphlang` (the PyPI name is `graflang`).
