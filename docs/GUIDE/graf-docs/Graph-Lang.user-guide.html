Graph-Lang: user guide

GraphLang is a graph-first language for agentic workflows: the *.graph.yaml file is the program, and the LLM mutates the topology instead of writing code. It is for multi-step, agentic work with branches, loops, risky actions, policy, audit or a person in the loop. It is not a general-purpose language: for one model call or a script, write the call or the script.

Installation

Requirements: Python 3.11 or newer, and a conda env or venv of your own (the repo's work has used a conda env named graf).

conda create -n graf python=3.11
conda activate graf
pip install -e ".[dev]"      # runtime + pytest

# optional: only for procedure_ref nodes
pip install -e ../SPL.py

To work on the shared libraries at the same time, install them from sibling checkouts first: pip install -e ../dd-llm -e ../dd-logging -e ../zinet.

Graphviz is a system program, not a pip package. It is needed for graf vis --engine graphviz images. Install it with sudo apt install graphviz (Ubuntu/Debian), sudo dnf install graphviz (Fedora), brew install graphviz (macOS), winget install Graphviz.Graphviz (Windows) or conda install -c conda-forge graphviz. Check with dot -V.

Core dependencies come with the base install: click, ruamel.yaml, networkx, jsonschema, cedarpy, dd-llm[openai], rich, dd-logging, zinet, dd-embed, plus numpy, requests and streamlit-ace. cedarpy is the official Cedar engine and is required, because grafr imports it at startup.

One console script is installed, graf. python -m graphlang ... does the same thing.

Check the install:

graf run cookbook/self_refine/self_refine.graph.yaml --param topic="rain"
graf vis cookbook/self_refine/self_refine.graph.yaml     # opens a picture in your browser
pytest

graf run uses claude_cli with claude-sonnet-5-5, so the claude command-line tool must work. Seeing ✓ Workflow completed means the runtime, schema validation and Cedar import all work. pytest has known failures (see Troubleshooting).

Quick start

  1. Install as above.
  2. Run a bundled workflow. This calls a real, billed LLM (the default adapter is claude_cli, model claude-sonnet-5-5):

``bash graf run cookbook/self_refine/self_refine.graph.yaml --param topic="rain" ``

The README example uses another adapter: graf run cookbook/code_pipeline/code_pipeline.graph.yaml --adapter ollama --param spec="Write a binary search function".

  1. Look at the workflow:

``bash graf info cookbook/self_refine/self_refine.graph.yaml graf vis cookbook/self_refine/self_refine.graph.yaml ``

  1. Cap model calls when you try a loop. Give graf run a --bind file that sets limits.max_llm_calls:

``bash printf 'limits:\n max_llm_calls: 4\n' > /tmp/cap4.yaml graf run cookbook/self_refine/self_refine.graph.yaml --param topic="rain" --bind /tmp/cap4.yaml ``

Architecture

A workflow is a YAML file. The loader validates it against a JSON schema and builds a networkx.MultiDiGraph. The runtime executes it as token-passing dataflow, calling one executor per node type. LLM calls go through adapters (dd-llm), and GUARD and MUTATE checks go through Cedar. The same file can be drawn (graf vis, through zinet), compiled to another form, or edited in an app.

flowchart LR
    Y["*.graph.yaml"] --> L["Loader + schema"]
    L --> R["Runtime (networkx)"]
    R --> N["Node executors"]
    N --> A["Adapters (dd-llm)"]
    N --> C["Cedar guard"]
    R --> S["Resolver"]
    Y --> V["graf vis (zinet)"]
    Y --> K["Compiler"]
    Y --> P["App (Streamlit)"]
  • Schema (graphlang/schema/): graflang-ir.json (node and edge schema, checked by the runtime; a missing schema is an error) and graph_delta.schema.json (the MUTATE delta).
  • Runtime (graphlang/grafr/): the interpreter.
    • runtime.py loads and runs the graph.
    • nodes/ holds one executor per node type.
    • expr.py is the safe condition evaluator.
    • adapters.py holds the mock adapter and the dd-llm adapters.
    • resolver.py resolves the resources block.
    • cedar_guard.py runs Cedar checks for GUARD and MUTATE.
    • topology.py backs graf validate.
    • procedures.py runs procedure_ref SPL workflows.
  • Compiler (graphlang/grafc/): mostly a stub. It holds a hand-written Cedar compiler (cedar/), Rust code generation (rust_gen/), describe and create.
  • Emitters (graphlang/grafe/): graph2spl.py writes a graph as .spl text, and graph2pocketflow.py writes a PocketFlow program.
  • Visualization (graphlang/grafv/): graf vis and the app (app.py, editor.py, pages/). The drawing engines live in zinet (zinet.vis); this folder holds the workflow style.
  • Docs generator (graphlang/grafd/): graf docs; the styles are files in graphlang/grafd/styles/.
  • Policies (graphlang/policies/): shared Cedar policies graph_safety.cedar and mutation_safety.cedar.
  • Recipes (cookbook/): example graphs with their prompts.

Concepts

The graph is the program

A GraphLang program is a YAML file, *.graph.yaml, starting with version: "1.0-graph". It has these top-level blocks:

  • workflow: name, inputs, outputs.
  • resources: procedures, prompts, policies (and parts).
  • nodes: typed nodes with ports and config.
  • edges: source and target as node.port, with a type.

Nodes do work; edges say what fires next and where data flows.

Node types

TypeRole
GENERATEA probabilistic agent: an LLM call.
EVALUATETests a condition and routes to pass or fail.
SOLVEA deterministic agent.
ASSERTA deterministic check.
FORK / JOINExplicit fan-out and barrier. FORK emits on all control ports; JOIN waits.
LOOPRuns its subgraph once per iteration; the condition is checked before each iteration.
BATCHMaps a subgraph over a list.
MUTATEThe self-revising operator: validates and applies graph deltas.
GUARDA policy checkpoint backed by Cedar.
RUNRuns a subprocess, a Python kernel or an http service.
QUERYReads a file, confined to the graph's folder. Risky.
EMITWrites to a file, stdout, a webhook or e-mail. Risky.
OBSERVEWrites to the log and observations.jsonl; never fails a run.
DECISIONA person as a node: terminal, --answer, or default. Interactive only.
RECOVERThe node an error route ends in.
INPUT / OUTPUTEntry and exit of the workflow.

SOLVE computes through one of four routes. A SOLVE with none of them is an error.

RouteWhat it does
expressionA safe expression.
procedure_refAn SPL workflow (needs SPL.py).
backend: kernelA persistent Python kernel (kernel extra).
backend: subprocessAny program, read through a declared parser. It may add container: {image, ...} (docker run, no network, read-only).

Edges and ports

Two edge types:

  • triggers: control tokens between ports such as complete, pass, fail, trigger, entry, exit.
  • binds: data, keyed by port name; the last writer wins.

Ports named in_<x> and out_<x> carry data. A node fires when a control token reaches its trigger; it reads its in_* ports and writes its out_* ports. A node's ports may be a name-to-type mapping (typed ports).

- {source: "draft.complete", target: "critique.trigger", type: "triggers"}
- {source: "draft.out_essay", target: "critique.in_essay", type: "binds"}

Token-passing execution

The runtime executes a workflow as token-passing dataflow. It is not true interaction-net rewriting (gap #26). Nodes may re-fire, so retry wires work. --max-steps bounds runaway loops; going over raises RunLimitExceeded. --workers enables a concurrent mode for parallel branches.

Three-tier composition and resources

  • Tier 1, inline: tiny prompts and expressions in the YAML.
  • Tier 2, reference: external .spl procedures, .md prompts, .cedar policies, declared under resources and referenced as prompt_ref: "prompts.draft" or procedure_ref: "procedures.x". Inside a prompt, {{in_topic}} is replaced with the value on the node's in_topic port.
  • Tier 3, sub-graph: a graph within a graph, for example a LOOP with a subgraph.

Compact form, parts and expand:

  • The compact steps: form expands to the full graph (graf expand); graf compact is the inverse, checked by expanding again.
  • Named subgraphs ("parts") listed under resources.parts and used as a SUBGRAPH node (compact use) are flattened in place when the graph loads. A part is a workflow file with one INPUT and one or more OUTPUT nodes. Parts can be named (cookbook:name[@hash]) and are held to the using graph's workflow.parts_policy.
  • The expand: block applies a part to every node of a graph of things; the edges become FORK/JOIN wiring. The first name for it was elaborate:, which is still read.
  • A MUTATE add_part delta can add a recipe from the node's catalogue at run time.

Cedar policies and fail-closed guards

Cedar policies back GUARD and MUTATE checks through the official engine (cedarpy). Checks are fail-closed: any evaluation error denies. Callers must pass every attribute the policies read. Risky nodes (RUN_CODE, QUERY, EMIT) must sit behind a GUARD, and graf validate finds unguarded ones.

MUTATE deltas

A MUTATE node checks a delta in this order: schema, structure, safety layer, Cedar, budget, then topology invariants on a trial copy (guarded risky nodes, no race, no JOIN deadlock). A delta can never:

  • remove or edit a GUARD or MUTATE node, or the risky flag;
  • add or change backend, code, result, command, parse or env_passthrough;
  • add or change the QUERY/EMIT keys file, channel, recipients, sender, smtp_host, smtp_port, allow_dirs (together CODE_KEYS).

The last two are refused before any policy runs, nested values included. A MUTATE inside a LOOP body affects only that iteration's copy, unless the loop sets persist_mutations: true.

Phases

A node with config.phases is wrapped in pre -> exec -> post. Phases give timeout, retry, fallback, out_schema, and routing on the result. An error route ends in a RECOVER node.

Conditions

Conditions use @var and the safe evaluator in expr.py (no eval; whitelisted functions; f-strings supported). Examples:

condition: "contains(@in_analysis, '[READY]')"
condition: "NOT @test_passed AND @cycle < @in_max_cycles"

@in_* are the node's own input ports. In a LOOP, @test_passed and @cycle are loop state (the previous iteration's outputs and the 0-based counter).

Two graph formats

Workflows (workflow: with nodes: and edges:) are executable. zinet graphs (primitives:, concepts:, applications:) are static dependency graphs. graf tells them apart by content and says what a zinet or ConceptBook file is instead of failing on a schema error.

Relation to SPL.py

SPL.py is the declarative workflow language that GraphLang builds on. GraphLang does not depend on it, except for procedure_ref (optional, lazy import). SPL.py's spl2graph lifts SPL workflows into GraphLang graphs (265 of its 274 cookbook workflows validate). graf compile --lang spl writes a graph back as SPL.

Configuration

Bindings file (--bind). Sets the model, files and limits per environment. Example: cookbook/self_refine/self_refine.bind.yaml. The key limits.max_llm_calls caps model calls.

Adapters. LLM calls go through dd-llm. Providers named in the sources are claude_cli (the default), ollama, openai, openrouter, deepseek, qwen, gemini_cli and echo. The openai SDK is a core dependency and serves openai, openrouter, ollama, deepseek and qwen; claude_cli, gemini_cli and echo need no SDK. anthropic and gemini need their extras. mock is for the test suite.

SPL_PY_PATH. Environment variable that makes SPL.py importable for procedure_ref nodes, as an alternative to pip install -e /path/to/SPL.py.

Logging. Logs go to ~/.graflang/logs by default; change them with --log-dir, --log-format and --log-level, or turn them off with --no-log. Nothing is logged until the CLI sets logging up.

Work area and settings (the app). ~/.graflang/ holds the work area: cookbook and solvers read-only, plus apps. --src-dir points the app at another folder. The settings file holds provider, model and API keys, and is written with mode 0600.

Workflow policy. workflow.parts_policy holds the parts a graph accepts.

Recipe search. Search combines meaning (dd-embed) with BM25. The embedding setting is chosen with --embedding in graf create. Tests set embedding: none so plain pytest is offline.

Limits

  • Early prototype: version 0.1.1, classified Alpha. graf run works end to end on the bundled workflows.
  • The Rust compiler is a stub. README.md and CLAUDE.md disagree on Cedar: the README roadmap marks Cedar integration done (GUARD and MUTATE checks via cedarpy), while CLAUDE.md says some README claims, such as Rust compilation and Cedar enforcement, are not implemented yet.
  • The hand-written Cedar compiler has known failing tests (gap #18); whether to keep it or use the official cedar-policy crate is an open decision.
  • Execution is token-passing, not true interaction-net rewriting (gap #26).
  • Human in the loop is only a design (docs/DEV/DESIGN/graflang-hitl.md) in the patterns page; the DECISION node covers the interactive case. RAG and token streaming are not built.
  • The app has no drag-to-connect on the canvas.
  • The paper is not submitted, and no draft is in the repository.
  • No experiments back performance claims. docs/DEV/DESIGN/graflang-experiments.md says Project A (the compliance batch) is built and Project B is not built.
