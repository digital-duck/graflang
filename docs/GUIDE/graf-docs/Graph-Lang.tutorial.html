Your first GraphLang workflow

You will install graf, run the bundled self_refine workflow, read its graph, then write a small haiku workflow with a retry loop. You need Python 3.11 or newer, a conda env or venv, and a working claude command-line tool, because the default model is claude_cli with claude-sonnet-5-5.

Step 1: Install GraphLang

Create an environment (conda is shown; a venv works too) and install the project from the repository root. The optional extras (anthropic, gemini, spl, vis, and others) are not needed here. graf compile --lang rust is an experimental stub, so do not use it.

conda create -n graf python=3.11
conda activate graf
pip install -e ".[dev]"

For a venv instead of conda:

python -m venv .venv
source .venv/bin/activate        # Linux / macOS

You should see: the graf command available in your shell (graf --help in the next step shows it).

Step 2: Check the install

Print the help, then validate a bundled workflow. Validation runs static checks and executes nothing.

graf --help
graf validate cookbook/self_refine/self_refine.graph.yaml

You should see: the command list, then a validation result. Check that it reports no problems. If you also run pytest, failures in tests/test_cedar_compiler.py and tests/test_policy_slicer.py are known (gap #18) and are not install errors.

Step 3: Inspect and run a bundled workflow

info shows the workflow's name, size, inputs, outputs and resources. run executes it. This is a real, billed model run: the default claude_cli adapter makes about three short calls.

graf info cookbook/self_refine/self_refine.graph.yaml
graf run  cookbook/self_refine/self_refine.graph.yaml --param topic="rain"

You should see: each node printed as it fires (⚡ GENERATE draft (#1) and so on), the output, a log: line with the path of this run's log file, and ✓ Workflow completed.

Step 4: See the graph

Draw the same workflow. This opens an interactive picture in your browser (the cytoscape engine is the default; --no-open and --engine are available).

graf vis cookbook/self_refine/self_refine.graph.yaml

You should see: a page where you can click a node to see its config and links. Check that nodes are coloured by type, triggers edges are solid and binds edges are dashed.

Step 5: Read the YAML

Open cookbook/self_refine/self_refine.graph.yaml. The graph is the program, so you read nodes and edges. There are an INPUT node (wf_entry), three GENERATE nodes (draft, critique, refine) and an OUTPUT node (wf_exit). Ports named trigger, complete, entry, exit carry control; ports named in_<x> and out_<x> carry data. Edges come in two kinds:

# control: who fires next
- {source: "draft.complete", target: "critique.trigger", type: "triggers"}
# data: where a value flows
- {source: "draft.out_essay", target: "critique.in_essay", type: "binds"}

A node fires when a control token reaches its trigger; it reads its in_* ports and writes its out_* ports. Prompts are files under prompts/, declared in resources.prompts and referenced as prompt_ref: "prompts.draft". Inside a prompt, {{in_topic}} is replaced with the value on the node's in_topic port.

You should see: the control chain entry -> draft -> critique -> refine -> exit in the triggers edges.

Step 6: Write your own workflow

Make a new folder with a prompt and a graph. First prompts/haiku.md:

Write a haiku about: {{in_topic}}

Then haiku.graph.yaml:

version: "1.0-graph"

workflow:
  name: "haiku_check"
  inputs:
    - {name: "topic", type: "TEXT"}
  outputs:
    - {name: "poem", type: "TEXT"}

resources:
  prompts:
    haiku: "./prompts/haiku.md"

nodes:
  - id: "start"
    type: "INPUT"
    ports: ["entry", "out_topic"]

  - id: "write"
    type: "GENERATE"
    config: {prompt_ref: "prompts.haiku"}
    ports: ["trigger", "complete", "in_topic", "out_poem"]

  - id: "gate"
    type: "EVALUATE"
    config: {condition: "len(@in_poem) > 10"}
    ports: ["trigger", "pass", "fail", "in_poem"]

  - id: "done"
    type: "OUTPUT"
    ports: ["trigger", "exit", "in_result"]

edges:
  - {source: "start.entry",    target: "write.trigger", type: "triggers"}
  - {source: "write.complete", target: "gate.trigger",  type: "triggers"}
  - {source: "gate.pass",      target: "done.trigger",  type: "triggers"}
  - {source: "gate.fail",      target: "write.trigger", type: "triggers"}   # retry

  - {source: "start.out_topic", target: "write.in_topic", type: "binds"}
  - {source: "write.out_poem",  target: "gate.in_poem",   type: "binds"}

The tutorial source I was given is cut off after the write.out_poem edge, so I cannot confirm the last edge that carries the poem to done.in_result. Check docs/GUIDE/TUTORIAL.md section 3 for the remaining edge(s) and add them before running; without them the output node receives no data.

You should see: two files, prompts/haiku.md and haiku.graph.yaml, side by side.

Step 7: Validate and run it with a cap

Validate first. graf validate also checks for races, deadlocks and unguarded risky nodes. The gate.fail -> write.trigger wire is a loop, and real model calls are billed, so give the run a bindings file that limits model calls.

graf validate haiku.graph.yaml
printf 'limits:\n  max_llm_calls: 4\n' > /tmp/cap4.yaml
graf run haiku.graph.yaml --param topic="rain" --bind /tmp/cap4.yaml

You should see: validation passing, then the nodes firing and the run finishing. Check that if the gate never passes, the run stops at the cap rather than looping forever.

What just happened

The graph is the program (steps 5 and 6): you wrote nodes and edges, not code. A run is tokens passing through typed nodes, with triggers edges carrying control and binds edges carrying data (step 3). EVALUATE routes to pass or fail, and the fail wire back to write.trigger is the retry (step 7). graf validate checks the graph before anything runs (steps 2 and 7). The default adapter is a real LLM, so runs cost money, which is why step 7 sets a cap.

Not implemented: Rust compilation is a stub, and the README's claims about Cedar enforcement go beyond what the hand-written Cedar compiler does today.
