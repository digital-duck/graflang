GraphLang

A graph-first language for agentic workflows.

The graph is the program; the LLM mutates topology instead of writing code.

https://github.com/digital-duck/graflang
GraphLang treats a YAML graph as the executable source of truth. It is an early prototype. The talk covers the idea, how a run works, safety, a demo recipe, and what is not done yet.

Outline

    The outline lists every slide title; click a line to jump.

    The problem

    • Frameworks such as LangGraph and AutoGen use Python code to describe a graph.
    • Safety ends up in scattered if/else guardrails.
    • Parallelism is asyncio.gather, with race conditions.
    • Self-revision means rewriting a Python file.
    These are the four pain points the README names for imperative frameworks. The rest of the talk answers each of them.

    The idea: the graph is the program

    Imperative frameworksGraphLang
    Source of truthPython code that describes a graphThe graph itself
    LLM's roleGenerate text/codeMutate the topology
    Parallelismasyncio.gather + racesExplicit FORK / JOIN
    SafetyScattered if/elseCedar policies
    Self-revisionRewrite the Python fileA validated graph delta
    The workflow lives in a *.graph.yaml file. The LLM outputs a validated graph delta rather than code. Cedar enforcement at run time applies to GUARD and MUTATE checks.

    What it is for, and what it is not

    Use it for

    ✔ multi-step agentic work
    ✔ branches and loops
    ✔ risky actions
    ✔ policy and audit
    ✔ a person in the loop
    • It is not a general-purpose language.
    • For one model call or a script, write the call or the script.
    • Under about five steps with no policy or audit need, the graph would be longer than the program.
    The user guide is explicit about when not to use GraphLang. Hello World is one generate step and an output.

    Anatomy of a graph file

    version: "1.0-graph"
workflow:
  name: "self_refine"
  inputs:  [{name: topic}]
  outputs: [{name: essay}]
resources:
  prompts: {draft: "./prompts/draft.md"}
nodes:
  - id: draft
    type: GENERATE
    ports: [trigger, complete, in_topic, out_essay]
edges:
  - {source: draft.complete, target: critique.trigger, type: triggers}
  - {source: draft.out_essay, target: critique.in_essay, type: binds}
    • triggers: control tokens between ports such as complete, pass, fail.
    • binds: data, keyed by port name.
    • Ports in_x / out_x carry data.
    The excerpt is abbreviated from the tutorial's self_refine walk-through. A node fires when a control token reaches its trigger, reads its in_ ports and writes its out_ ports.

    Node types

    TypeRole
    GENERATEprobabilistic agent: an LLM call
    SOLVE ASSERTdeterministic: expression, Python kernel, or subprocess
    EVALUATEa condition with pass and fail paths
    FORK JOINexplicit fan-out and barrier
    LOOPcyclic control flow, test-gated retry
    MUTATE GUARDself-revising operator; Cedar policy checkpoint
    There are more node types, for example QUERY, EMIT, OBSERVE, RUN and BATCH, but these are the core ones. SOLVE can run SymPy, Z3, Lean or a Rust binary as a subprocess read through a declared parser.

    How a run works

    • The YAML loads into a networkx.MultiDiGraph and runs as token-passing dataflow.
    • Nodes may re-fire, so retry wires work.
    • JOIN is a barrier; FORK emits on all control ports.
    • --max-steps bounds runaway loops.
    • It is not true interaction-net rewriting (gap #26).
    The LOOP node runs its subgraph once per iteration and checks the condition before each iteration. Data edges are last-writer-wins.

    Three-tier composition

    TierWhat
    1 Inlinetiny prompts and expressions in the YAML
    2 Referenceexternal .spl procedures, .md prompts, .cedar policies
    3 Sub-grapha graph within a graph: a LOOP body, or a part used as a SUBGRAPH node

    The compact steps: form expands to the full graph (graf expand).

    Parts are flattened in place when the graph loads, so the runtime itself has no SUBGRAPH semantics.

    Safety: Cedar guards and safe MUTATE

    • GUARD and MUTATE checks run through cedarpy, fail-closed: any evaluation error denies.
    • A delta can never remove a GUARD or edit the risky flag.
    • A delta may not add or change code-bearing keys such as code, command, parse.
    • graf validate finds races, deadlocks and unguarded risky nodes before anything runs.
    MUTATE validates schema, structure, safety layer, Cedar and budget, then topology invariants on a trial copy. The README claim of Cedar enforcement is limited to GUARD and MUTATE checks.

    Making runs dependable and affordable

    • Per-node retry, timeout, fallback and output schemas; typed ports.
    • Budgets such as limits.max_llm_calls in a --bind file.
    • A run summary with calls, tokens and time.
    • --record / --replay of model calls, so tests need no model.
    • --checkpoint / --resume after a failure.
    Real-LLM runs are billed, so a cap matters: a loop once ran many billed calls. Token counts from claude_cli are estimates.

    Example: code_pipeline

    - id: test_gated_loop
  type: LOOP
  config:
    condition: "NOT @test_passed AND @cycle < @in_max_cycles"
    subgraph:
      nodes: [gen, rev, test, guard]
      edges:
        - gen.complete   -> rev.trigger
        - rev.complete   -> test.trigger
        - test.complete  -> guard.trigger
        - guard.allow     -> gen.trigger  # safe retry
    • A test-gated LOOP with a GUARD before each retry.
    • Eight SPL procedures, 00 to 07, next to the graph.
    The excerpt is condensed from the README; edges are shown as arrows for space. Running the procedures for real needs SPL.py importable.

    Demo: compliance audit

    extract_pii (LLM) -> check (rules) -> compliant?
   yes -> release_guard (Cedar) -> released
   no  -> redact (LLM) -> extract_again (LLM)
          -> recheck -> compliant?
               no  -> escalated (human)
               yes -> release_guard
    • The model finds the types of personal data; rules decide.
    • A Cedar policy has the last word before release.
    • Anything not shown compliant ends at escalated.
    Demo graf vis cookbook/compliance_audit/compliance_audit.graph.yaml, then a run on customer_case_file.txt with a call cap.
    The recipe is an illustration of the pattern, not legal advice; the rules are not a real GDPR or PCI rule set. A failing document costs 3 model calls per run.

    Compliance audit: what was measured

    • batch_test.py runs documents x variants x models x repeats and stores results in SQLite.
    • First haiku batch: 54 runs, no false release.
    • One real run took 18.0 s; LLM calls took 3.4 to 9.9 s.
    • The rule check took a few milliseconds in-process.
    • Graph traversal is under 0.1% of the run.
    The timings are one run on one machine, so indicative only. The analysis script reports Wilson intervals and a paired McNemar comparison.

    Relationship to SPL.py

    • SPL.py is the declarative workflow language that GraphLang elevates.
    • spl2graph lifts SPL workflows to graphs: 265 of 274 cookbook workflows validate.
    • graf compile --lang spl goes back.
    • GraphLang does not depend on SPL.py, except for procedure_ref.
    • LLM calls go through the shared dd-llm package.
    The 47 solver recipes of SPL.py were migrated into cookbook_solvers and run with a real model.

    Is Rust worth it?

    • The Rust target is a stub; graf compile to Rust is experimental.
    • Graph traversal is under 0.1% of a run, so speed is not the reason.
    • Rust would cut about 0.3 s of Python start-up per CLI call.
    • The case for Rust is safety, not speed: memory safety together with Cedar.
    This is the maintainer's view, based on one measurement with the mock adapter. A Rust target would have to reimplement the expression language, the LLM adapters and the SPL procedure calls.

    What is not done yet

    • Rust compilation is a stub.
    • The hand-written Cedar compiler has known test failures (gap #18).
    • Human in the loop is only a design note; no RAG; no token streaming.
    • No drag-to-connect in the app; no paper draft.
    • No experiments yet support performance claims; Project B is not built.
    The README is partly aspirational. Project A, the compliance batch store, is built; Project B, the intent-invariance round trip, is a plan awaiting review.
